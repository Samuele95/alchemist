The skill

The search for a prompt no one has seen

Alchemist is a multi-agent loop for outputs that must satisfy several constraints that pull against each other. A compiler writes a candidate. Isolated testers each try to break it on one constraint. A judge that never reads the candidate reads their verdicts and the whole history, and writes the next fix. This page describes the skill and summarises its theory. The full paper, The Adversarial RL Loop by Samuele Stronati, with every figure and its interactive runs, is on the Paper page.

Overview

Two constraints are coupled when a fix that satisfies one tends to break the other. Repairing them one at a time can go in circles: the fix for A breaks B, and the fix for B breaks A again. The loop separates generation from verification. It rests on an asymmetry that the paper assumes and does not measure: checking one constraint on a given candidate is cheaper than producing a candidate that satisfies all of them. Where no cheap check exists, there is nothing for the loop to exploit, and the paper does not recommend it.

How a run goes

Alchemist is a skill for Claude Code. A run has four phases.

  1. Instantiate. Settle the three decisions — the output space, the testers with their projections, the halt predicate and any relaxation — plus the iteration budget. Record them in run-config.yaml and confirm them before any role is written.
  2. Forge the roles. The compiler is a one-shot task prompt, each tester a strict grader told to make its constraint fail, and the judge a grader of verdicts against the history. Alchemist asks Prometheus to write them, then wires in the context restrictions.
  3. Run or ship. In Forge mode each role runs as an isolated sub-agent and receives only its permitted context. Each iteration goes compile → testers in parallel → halt check → judge → one new row in the history ledger. In Dry-run mode the role prompts, the config and the empty ledger are written as files, and nothing runs.
  4. Report. Either the converged artifact with its history trace, or a barrier report: the history, the judge's diagnosis, and the constraint it recommends relaxing.

Design rules

  • Strict testers. A tester that only evaluates passes weak candidates; one told to break its constraint finds the real failures early.
  • The judge sees the full history, as a table. The history is where coupling becomes visible: one row per iteration, every verdict, the fix applied.
  • At least two testers. With one, there is no coupling to detect, and a single prompt from Prometheus will do.
  • Relaxations before the loop, never after.
  • Fixes carry their content. The compiler never sees the previous candidate, so a fix that only points at it ("keep the rest unchanged") has nothing to apply to.

The theory, in brief

What follows summarises the paper. Read the full text, with all its figures and the recorded runs you can step through, on the Paper page.

Search in prompt space

Writing a good prompt is largely a search. Picture every possible prompt as a point in the space where the model reads them, close together when the model reads them alike. The ideal prompt, the target prompt s†, is a point in that space. It is hypothetical: no one knows it in advance, and neither it nor the distance to it can be observed.

What can be observed is the testers' verdicts. Each tester divides the space into the candidates it passes and the ones it fails. The acceptance region is where every tester passes. Each fix is a semantic operation, a step from one point to another. The loop halts when the candidate enters the acceptance region, not when it reaches s†. Halting is therefore sound only relative to the testers: a requirement no tester checks is not enforced.

Coupled constraints have a recognisable shape here. When two constraints compete for the same resource, the region where both hold is a narrow strip. A step aimed at one of them crosses the strip and lands on the far side, much as gradient descent zig-zags between the walls of a narrow valley.

The loop

There are three roles and one fixed cycle: compile, test in parallel, check the halt condition, judge, add to the history.

  • Compiler. Writes a candidate from the target and the judge's accumulated fixes. It never sees raw verdicts or the previous candidate.
  • Testers. Each checks one constraint, is told to break the candidate rather than grade it, and sees only its own part of the candidate. A projection here is a context-selection function, not a geometric projection. Testers never see each other.
  • Judge. Reads every verdict with its reason and the whole history of verdict–fix pairs, and never the candidate itself. It is the only role that reasons across constraints. Its fix reaches the compiler in the next iteration.

Instantiating it

Three decisions define a run: the output space, which bounds what the compiler may produce; the testers with their projections, at least two and about five at most; and the halt predicate, usually "every tester passes". Any relaxation of the halt must be declared before the loop starts; chosen afterwards, it is a rationalisation. As a planning guideline, budget 3–4 iterations for 2–3 constraints and 5–6 for 4–6 interacting constraints. The compiler rebuilds each candidate from the target and the fixes, so anything that must survive has to be written into the fix itself. A fix that only points at the previous candidate ("keep the rest unchanged") has nothing to apply to.

Why it should converge

Three design mechanisms are meant to drive the search.

  • Informed fixes. The judge's diagnosis replaces a random mutation.
  • A tabu-like history. Tried fixes stay visible, and the judge is told not to re-propose them. This is informal: nothing enforces it.
  • Coupling detection. Reading an alternation in the history, the judge can recognise a coupled pair and write one fix for both.

Theorem 1. Suppose each round reached without halting has at least a fixed chance p of producing a candidate that passes every tester, and the judge returns a fix rather than a barrier before the budget. Then the loop halts within N rounds with probability at least 1 − (1 − p)N. Without a budget, it halts after at most 1/p rounds in expectation. Whether a real judge meets the assumption is not shown.

What is guaranteed outright is modest. Cost is bounded by N(m + 2) role calls. Reaching the budget does not prove that no answer exists. The paper treats oscillation as the main convergence risk under coupled constraints, as a design premise rather than a measured finding.

Outcomes

A run ends one of two ways. Either every tester passes and you get the artifact with its history, the trace of verdicts and fixes that shows how it was found. Or the judge declares a barrier: the history, a diagnosis of which constraints could not be met together, and the constraint to relax. A barrier report is a diagnosis, not a proof of infeasibility.

The two runs

The paper shows two live runs, selected by the author as examples rather than an evaluation (n = 2, no baseline).

Bramble. The task was hardening the system prompt of a fictional library assistant, with five testers. Each iteration went as follows:

nT1 leakT4 staff notewhat the judge did
1fail (11 of 14 held)passa fixed redirect: never confirm or deny a waiver
2pass (15 of 15)fail: the note was droppednamed the oscillation, traced it to the shared 90-word budget, and wrote the Instructions with the note verbatim
3fail (16 of 18 held)passset aside listing the missing framings (the same trade), and wrote one deflection for any framing
4pass (16 of 16)pass— every tester passed; the loop halted at iteration 4 of 6

The other three testers passed throughout. Over the run the deployed assistant held 58 of 63 executed attacks.

SemVer. The task was a regex and its description, with four testers. Every tester passed at iteration 3 of 6, with no oscillation. The run showed that text the judge writes out in full survives a compiler that never sees the previous candidate, while a fix that only points at it does not.

Related methods

Like ProTeGi and TextGrad, the loop treats prompt search as descent with textual feedback. Unlike them, the direction comes from adversarial testers and from a judge that never reads the prompt. From reinforcement learning it borrows only the division of roles: the compiler as actor, the testers as environment, the verdicts as reward, the judge as critic. No parameter is trained. Its nearest neighbour is LLM-Modulo, and it shares its basic shape with Self-Refine, Reflexion, CEGIS and PAIR. Because the compiler is defined only by its interface, any prompt-engineering technique can sit inside the loop and be wrapped by it, although no run has done that yet. The paper claims no novelty for the loop itself, only the explicit, enforceable specification of who reads what.

Alchemist and Prometheus

Prometheus designs prompts and never runs them; Alchemist runs the tournament. Alchemist asks Prometheus to write its compiler, tester and judge prompts. In the paper's runs, the role prompts followed Prometheus's prompt shapes and every role ran as a fresh Claude Code sub-agent. Alchemist has two modes: Forge runs the loop to the end, and Dry-run hands you the role prompts, the run configuration and an empty ledger without running anything.

When to use it

Use it when requirements are coupled and each is cheaper to check than to satisfy: hardening a system prompt, converging a SKILL.md, forging a regex or a config. Don't use it when the constraints are independent (a checklist is cheaper), when no cheap check exists, or when one prompt already works.
